Introduction to TestGenie

TestGenie is an AI-powered web automation system that combines artificial intelligence, browser automation, and enterprise-grade infrastructure to deliver unprecedented efficiency and reliability in software testing.

This tool automatically generates Playwright-based TypeScript automation scripts from BDD feature files and seamlessly integrates them into your team's automation codebase repository on GitHub.

Key Achievement: 3-12 minute total processing time with 95%+ success rate

Getting Started

Follow these steps to get started with TestGenie:

  1. Navigate to: https://chewy-genai-automation.corp-ai-workloads.stg.aws.chewy.cloud/TestGenie
  2. Sign in with your credentials
  3. Select your project domain from the dropdown
  4. Prepare your BDD feature file
  5. Upload the feature file
  6. Configure script generation options
  7. Monitor execution status
  8. Download generated scripts and video recordings

Create Steps

The Create Steps feature allows you to manually create and refine test steps before script generation.

How to Use:

  1. Go to Create Steps in the left sidebar
  2. Enter your test workflow description
  3. Configure additional settings as needed
  4. Click Generate to create the automation script
  5. Preview and customize the generated steps
  6. Submit to save your workflow
Tip: Use clear, descriptive language when describing your workflow to get better AI-generated steps.

Generate Scripts

Convert your BDD feature files into fully functional Playwright automation scripts.

Step-by-Step Process:

  1. Select your Project Domain from the dropdown (required)
  2. Click "Upload feature file" and select your .feature file in BDD Gherkin format
  3. Configure options:
    • Include API Calls - Check if you have JSON files for API calls
    • Execution Engine - Choose MCP (recommended) or JavaScript crawler
    • Generate BDD Scripts - Unselected by default. Get Playwright scripts; select for BDD format
    • Show script design preview - See feature file and sample locators before execution
  4. Click "Generate" to start the process (typically 20 minutes)
  5. You'll receive a Slack notification when complete
  6. Download generated scripts and video of execution
Important: Project Domain is mandatory for all script generation requests. Processing typically takes around 20 minutes depending on feature file length.

Creating Feature Files

Feature files define your test scenarios in BDD (Behavior Driven Development) format.

Feature File Best Practices:

  1. Start with a login step or account creation as needed
  2. Write each step in clear, descriptive language
  3. Always include verification steps at the end
  4. Use consistent naming conventions
  5. Reference URLs and element names precisely

Example Feature File:

@example-tag-123
Feature: Checkout - PayPal Purchase Flow Without Saved PayPal Method (Buy Once)
@scn-tag-123
Scenario: Verify PayPal Checkout buttons are displayed
    Given the user creates a new user account
    Then user navigates to "https://www-stg.chewy.net/product/dp/12345"
    Then user clicks on "Buy once" Radio button
    Then user clicks on "Add to Cart"
    Then user clicks on "Proceed to Checkout"
    Then user enters "First and Last Name" as "Playwright Test"
    Then user enters "Street Address" as "123 Main St"
    Then user enters "City" as "Boston"
    Then user select "State" as "MA"
    Then user enters "02101" in the "ZIP Code" field
    Then user enters "Phone Number" as "(617) 555-0123"
    Then user clicks on "Ship to this address"
    Then user clicks on radio button "PAYPAL"
    Then the user verifies that "PayPal Checkout" button is displayed
Note: Feature files should be added to src/tests/features directory. See sample files here.

Example Table (Data-Driven Tests)

Run the same test scenario multiple times with different test data using Example Tables. This allows you to test the same feature with various inputs without writing duplicate scenarios.

What is an Example Table?

An Example Table is a data table that contains test data for a Scenario Outline. Each row in the table represents a separate test run with different values.

When to Use Example Tables:

  • Testing the same workflow with multiple user accounts
  • Validating form inputs with different data combinations
  • Running the same purchase flow with different payment methods
  • Testing search functionality with different search terms
  • Verifying reports with different filter combinations

Quick Example 1:

Scenario Outline: User Registration
  Given user navigates to registration page
  When user enters "Email" as <email>
  And user enters "Password" as <password>
  Then user account is created successfully

  Examples:
    | email            | password    |
    | user1@chewy.com  | Pass123!    |
    | user2@chewy.com  | Pass456!    |
    | user3@chewy.com  | Pass789!    |

Quick Example 2:

Scenario Outline: Navigate to different pdp pages
  When user navigates to "<baseUrl>"
  Then user navigates to "<firstProductUrl>"
  Then user clicks on the "Set Up Autoship" button
  Then user navigates to "<secondProductUrl>"
  Then user clicks on the "Set Up Autoship" button

  Examples:
    | baseUrl                   | firstProductUrl               | secondProductUrl                      |
    | https://www-stg.chewy.net | https://www-stg.chewy.net/abc | https://www-stg.chewy.net/xyz        |

Quick Example 3:

Scenario Outline: Navigate to pdp and add shipping data
  When user navigates to "<baseUrl>"
  Then user navigates to "<productUrl>"
  Then user clicks on the "Set Up Autoship" button
  Then the user clicks on "Proceed to Checkout"
  Then user enters shipping details:
      | field               | value      |
      | First and Last Name | <fullName> |
      | Street Address      | <street>   |
      | City                | <city>     |
      | State               | <state>    |
      | ZIP Code            | <zip>      |
      | Phone Number        | <phone>    |
  When user clicks on "Ship to this Address"

  Examples:
    | baseUrl                   | productUrl                    | fullName        | street               | city   | state | zip   | phone            |
    | https://www-stg.chewy.net | https://www-stg.chewy.net/abc | Playwright Test | 4 Northeastern Blvd | Nashua | NH    | 03079 | (077) 788-8777 |

How to Write an Example Table:

  1. Use Scenario Outline: instead of Scenario:
  2. In your steps, use angle brackets for placeholders: <email>, <password>
  3. Add Examples: section at the end
  4. Create a table with:
    • Header row: column names (must match your placeholders)
    • Data rows: actual test values

Key Points:

  • Each row runs as a separate test automatically
  • Placeholder names (between angle brackets) must exactly match column headers
  • Use | (pipe) symbols to separate columns
  • The first row after Examples: must be headers
  • Each data row creates one complete test execution

Best Practices:

  • Keep test data realistic and representative
  • Include edge cases (empty values, special characters, maximum length)
  • Use 3-5 examples per scenario for balance
  • Use descriptive column headers
  • For sensitive data, use AWS Secrets Manager placeholders: <awssecretmanager.credential_name>
Pro Tip: The system automatically creates unique accounts per row when using Example Tables. If you have 5 rows, it will create 5 different user accounts and run 5 separate tests - all from a single Scenario Outline!

Common Steps

Create reusable test step templates that you can use across multiple scenarios and projects.

Add/Preview Common Steps:

  1. Go to Common Steps in the sidebar and click Add/Preview tab
  2. Fill in the fields:
    • Key Line - unique identifier for the common step
    • Common Steps - list of test steps (one per line)
    • Domain - select the domain this applies to
    • Has API Steps - check if API calls are involved
    • Default Parameters - optional JSON for parameters
  3. Click Preview to see how steps will appear
  4. Click Save to store in the database

View/Search Common Steps:

  1. Go to Common Steps → View/Search tab
  2. Select a domain and enter search criteria
  3. Click Search to find existing steps
  4. Select and delete steps as needed

Auto-Heal

Automatically repair failing test scripts by updating broken locators and fixing execution issues.

How Auto-Heal Works:

  1. Navigate to Auto-Heal in the sidebar
  2. Select a Module to analyze
  3. Click Search to find scenarios that need healing
  4. Review the results showing:
    • Feature and scenario information
    • Current vs. updated scripts
    • Locator map changes
  5. For each scenario:
    • Click AUTO HEAL to trigger the healing process
    • Review the updated script
    • Click Accept to apply changes or Reject to discard
Current Accuracy: 95% success rate with comprehensive error handling

API Integration & JSON Files

Use API calls to set up test data and perform backend operations within your automation tests.

JSON File Format:

Create a JSON file containing URL, method, headers, and body for API calls:

{
  "url": "https://stg-use2-apt-shared-main.plat.stg.aws.chewy.cloud/eks/app/account-orchestrator/v1/test/accounts",
  "method": "POST",
  "headers": {
    "accept": "application/vnd.api+json",
    "Content-Type": "application/json"
  },
  "body": {
    "accountType": "REGISTERED",
    "password": "YOURPASSWORD",
    "u2sClientId": "storefront-dummy-id",
    "enabled": true,
    "email": "playwright.test+{timestamp}@example.com",
    "firstName": "Playwright",
    "lastName": "Test"
  }
}

Using API Responses in Feature Files:

Reference API responses in your feature file steps:

And user add Header "Authorization: Bearer {NewUserAuthToken}" in session service
And user add "loginId: {accountResponse.loginId}" to session body
Note: To execute TS files with API steps, api.service.ts is needed to handle JSON invocation, header/body modification, and API response storage.

Cookie Extraction

Extract and manage cookies from browser sessions for use in subsequent test steps and API calls.

How Cookie Extraction Works:

  1. Use the cookie extraction step after completing a login or authentication flow
  2. Cookies are automatically captured from the current browser session
  3. Store cookies with a descriptive name for later reference
  4. Reference stored cookies in subsequent steps or API requests

Cookie Extraction in Feature Files:

Extract cookies after login and use them in subsequent steps:

Then user extracts cookies as "login_cookie"
Then user add Header "Authorization: Bearer {login_cookie.JWT}" in account service
Then user enters "Search" as {login_cookie.rxVisitor}

Cookie Structure:

Extracted cookies are stored as key-value pairs with the following properties:

  • name - Cookie identifier
  • value - Cookie value
  • domain - Domain the cookie applies to
  • path - Path the cookie applies to
  • expires - Expiration timestamp (if applicable)

Using Extracted Cookies:

// After extracting cookies as "session_cookies"
// Reference specific cookie values in feature steps:
Then user enters "Email" as {session_cookies.email}
Then user clicks on {session_cookies.buttonName}
Then user add Header "Authorization: Bearer {session_cookies.authToken}" in service
Note: Cookie data is automatically converted to key-value pairs for easy reference in subsequent steps. Use dot notation to access specific cookie properties (e.g., {login_cookie.JWT}).

Mock API Integration

Use Mock API to intercept and simulate HTTP responses during testing. This is useful for testing scenarios without making real API calls.

How Mock API Works:

  1. Create a JSON mock file with the response structure you want to simulate
  2. In your feature file, use the MOCKS step before the action that will trigger the API call
  3. The mock response will be returned instead of the actual API call
  4. Continue with your test steps using the mocked response

Mock JSON File Format:

Create a JSON file containing the mock response structure:

{
  "status": 200,
  "route": "**/api/checkout/v3/shipping-address",
  "method": "POST",
  "response": {
    "order": {
      "id": 5011021576,
      "status": "P",
      "currency": "USD",
      "totalItemQuantity": 1,
      "shippingAddress": {
        "firstName": "Playwright",
        "lastName": "Test",
        "street1": "123 Main St",
        "city": "Boston",
        "state": "MA",
        "zip": "02101"
      },
      "shippingMethod": {
        "id": "standard",
        "name": "Standard Shipping",
        "cost": 5.99
      }
    }
  }
}

Using Mock API in Feature Files:

Use the MOCKS step to activate the mock before the action:

Then user MOCKS with "mock_post_shiptothisaddress.json"
Then user clicks "Ship to this address" button
Then the user verifies that shipping address is saved
Then the user verifies that "Standard Shipping" option is displayed

Mock JSON Structure:

  • status - HTTP status code (200, 201, 400, 500, etc.)
  • route - URL pattern to match (supports wildcards like ** or *)
  • method - HTTP method (GET, POST, PUT, DELETE, PATCH)
  • response - JSON response body that will be returned by the mock

Mock Files Location:

Place mock JSON files in your project's mock data directory (typically alongside your feature files or in a dedicated mocks folder).

Pro Tip: Use wildcards in routes to match multiple similar endpoints:
  • **/api/checkout/** - Matches any checkout endpoint
  • **/api/order/* - Matches specific order operations
  • ** - Matches any endpoint (use with caution)

Running Tests Locally

Prerequisites:

Set a custom user-agent to bypass bot detection and security blocks:

const contextOptions: any = {
  viewport: { width: 1920, height: 1080 },
  userAgent: 'MyLoadTestingAgentString/1.0/...'
};

File Organization:

  1. Feature files go to: src/tests/features
  2. Step definition files go to: src/tests/steps
  3. Feature and step definition files must have the same name
    • Example: Pay10066.feature & Pay10066.ts

Tagging Conventions:

@bnpl @Pay10066                 // All tests in directory + specific file
@bnpl - triggers all tests in a directory
@Pay10066 - triggers all scenarios in a feature file
@bnpl-10066 - triggers a specific scenario

Running Tests Locally:

npx cucumber-js --tags "{@bnpl-10066}"

Security & Credentials

Secure Credentials with AWS Secrets Manager

What it is: A secure vault where we keep sensitive items (API tokens, passwords, keys).

Why It Matters:

  • Nothing sensitive is hardcoded or shared in plain text
  • The app fetches what it needs only when it needs it
  • Credentials are encrypted and securely stored in AWS

How It Works (At a Glance):

  1. Your team's tokens/credentials are stored once in a secure AWS vault
  2. When the app needs one (for example, to call an API), it securely retrieves it from the vault
  3. The secret never shows up in the UI, logs, or code

Using AWS Secrets in Feature Files:

Reference AWS Secrets Manager credentials using the {awssecretmanager.secret_name} placeholder format:

@Deals @Deals001
Feature: Adding Details
@Deals-001
  Scenario: Test new Playwright
  Given user navigates to "https://rebates-platform-ui.demm.stg.aws.chewy.cloud/deals"
  And user enters "Username" as {awssecretmanager.galileo_username} on Login page
  And user clicks on the "Next" button
  And user enters "Password" as {awssecretmanager.galileo_password} on Login page
  And user clicks on the "Verify" button
  Then the user verifies that "Deal List" text is displayed

What You Need to Do:

Normally, nothing. The app takes care of secret retrieval automatically.

AWS Account Access (Optional):

For log access and monitoring, you may need PowerUserAccess to the following AWS accounts:

  • corp_ai_workloads_stg - Staging environment
Security Best Practice: Never hardcode credentials in your feature files or code. Always use the {awssecretmanager.secret_name} placeholder to reference stored credentials.

Troubleshooting & FAQ

Q: Why is my test taking longer than expected?

A: Test generation typically takes 10-20 minutes depending on feature file complexity. Intelligent caching can reduce processing time by up to 40%.

Q: How accurate are the generated scripts?

A: Current accuracy is ~95%. Always review generated scripts line by line to verify locators and steps.

Q: Can I run tests locally before merging to repository?

A: Yes! Use the local testing commands with Cucumber-js. Ensure feature and step definition files are in the correct directories with matching names.

Q: What if a test fails?

A: Use the Auto-Heal feature to analyze and repair failing tests. Review the video recording and screenshots for detailed failure context.

Q: How do I handle API authentication in tests?

A: Use AWS Secrets Manager for credentials. Reference them in your feature files or extract cookies post-login using the cookie extraction feature.

Q: Can I use TestGenie for non-Chewy.net applications?

A: Yes! TestGenie can generate automation scripts from any web application, though current samples cover chewy.net and Rhapsody.

Q: How do I download test videos?

A: After execution, look for download links in run output, pipeline logs, or Slack notifications. Videos are stored in AWS S3.

Q: Who do I contact for help?

  • Secret additions/rotations: Platform/DevOps team
  • Video access issues: QA/Automation team
  • TestGenie features: TestGenie team
